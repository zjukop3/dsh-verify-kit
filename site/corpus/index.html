规则在测试里被观察到两个方向，只说明"我想到的情况它判对了"。真正的证据是把检查指向别人写的文件，看它会不会误报、能不能抓到真错。下面是实测——每个数字都由 test/third-party-corpus.test.js 重新推导，页面上写的东西和代码做的事只能是一件事。

第三方语料（别人写的 39 份 README）

检查看了什么报了什么怎么解读
tablelint37 份 README 里的 100 张真实表格0（修掉一个误报之后）它一开始报了 4 次 empty-header，全部是故意的无表头表格：一类是 | | | 做的视觉分栏，一类是第一列放粗体行标签。已改成豁免这两种形状，其余列仍报
numberlint39 份 README 的全部数字写法2 条 thousands-inconsistent两条都是真发现：同一份文档的两种译文里，同一个数量写成 1,500 和 1500。三十九份文档只报两次，且集中在同一个仓库的两份译文——这是精确，不是噪音
outline-lint39 份 READMEno-conclusion 39 次不是缺陷，是我点错了检查器：它判的是"研究报告有没有先给结论"，而 README 不是研究报告。强行让 README 通过这条，等于把标准降到没有意义
citelint本仓库文档—没有第三方语料。别人的 README 里没有引用编号体系
hashcheck本仓库交付文件—针对清单与磁盘的比对，第三方语料不适用

缺陷记录

#检查 / 规则问题修复
1outline-lint / empty-heading死规则：标题正则要求 #{1,6}s+ 后还有非空文本，而"标题文字被删空"正是这条规则存在的理由，它永远看不到。我为证明它会触发而写的测试，证明了它触发不了0.1.4，## 单独一行现在报 empty-heading
2十条规则只有单向测试：outline-lint 3 条、tablelint 4 条、numberlint 1 条、hashcheck 1 条从没在测试里被触发过；citelint 则完全没有"干净文档产出零 finding"的用例全部补齐，现在 25/25 双向

第 1 条是 scripts/audit-rules.mjs 找出来的——这个审计要求每条规则都被观察到两个方向。第 2 条是它第一次跑出来的结果：10/26。

这个审计本身

审计不是万能的：它分不出"死规则"和"没人写触发测试"。一条没有触发测试的规则，两种情况的症状完全一样，只有人去写那条测试才会知道是哪一种。第 1 条就是写测试的人写了测试、然后发现它不会红。
